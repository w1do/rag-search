## Why

Vector (RAG-сервис базы знаний) пока состоит только из каркаса монорепо (этап 1 из `PLAN.md`). Нет доменной модели, авторизации, проектов, загрузки знаний, поиска и интерфейса. Нужна одна детальная спецификация `vector-kb`, описывающая всё приложение, чтобы реализовать его за один проход с чистой структурой и поддерживаемым кодом.

Проблемы, которые решаются:
- владельцу негде создавать проекты и управлять знаниями и ключами;
- агентам нужен безопасный поиск по знаниям конкретного проекта через API/MCP;
- без единого контракта слои (API, воркер, UI) разойдутся, а доступ к данным окажется размазан по коду.

## What Changes

- **Авторизация**: вход в веб-UI и API по `EMAIL`/`PASSWORD` из `.env`; агенты используют `MCP_TOKEN`.
- **Проекты**: создание, список, переименование, удаление с каскадной очисткой данных и индексов.
- **API-ключи**: выпуск на проект, секрет показывается один раз, в БД хранится только хеш, отзыв, изоляция между проектами.
- **Знания**: файлы (txt, md, pdf), произвольный текст, ссылки; просмотр, редактирование, удаление; асинхронная индексация через очередь задач.
- **Версии**: правка создаёт версию N+1, старые версии доступны, в поиске участвует последняя.
- **Поиск и контекст**: эндпоинты с обязательным `project_id`, гибридный поиск (Qdrant + Typesense), fallback на полнотекстовый при недоступности векторного индекса.
- **Очередь и воркер**: очередь в PostgreSQL (`FOR UPDATE SKIP LOCKED`), повторы при сбоях, переиндексация.
- **Веб-UI**: страницы «Проекты» и «Знания», единый API-клиент и дизайн-система, состояния загрузки, пустого списка и ошибки.
- **Архитектура**: слои router → service → repository; Protocol-интерфейсы репозиториев в `vector_core`, SQL-реализации и in-memory fakes для тестов.
- **Принятые допущения** (закрывают открытые вопросы): поддерживаемые типы файлов — `.txt`, `.md`, `.pdf`; лимит загрузки по умолчанию 10 МБ (настраивается переменной окружения с значением по умолчанию); `MCP_TOKEN` даёт агенту доступ к поиску, при этом `project_id` по-прежнему обязателен и проверяется.

### Вне рамок (Non-Goals)
- n8n и любые внешние SaaS-интеграции.
- Многопользовательская модель и роли (один владелец из `.env`).
- Ручная настройка вне `.env`.
- Реализация в рамках этого артефакта: здесь только планирование.

## Impact

- **Код**: `apps/api` (роутеры, сервисы, авторизация), `apps/worker` (обработчики задач индексации), `apps/web` (React-страницы, API-клиент, компоненты), `vector_core` (сущности, Protocol-репозитории, SQL-реализации, миграции), `vector_cli` (переиндексация, служебные команды).
- **Данные**: схема PostgreSQL (`projects`, `api_keys`, `sources`, `source_versions`, `jobs`); индексы Qdrant и Typesense как производные.
- **Инфраструктура**: `docker-compose.yml` с фиксированными версиями образов; `.env.example` с `EMAIL`, `PASSWORD`, `MCP_TOKEN`.
- **Ограничения**: версии зафиксированы (без `latest`), секреты только из vault и не попадают в код, YAML, `.env.example`, логи и коммиты; без n8n.
- **Риски**: большой объём в одном проходе (смягчается группами в `tasks.md`); рассинхрон индексов (PostgreSQL остаётся источником истины, индексы перестраиваются задачами).
- **Документы**: после реализации `PLAN.md` (этапы 3–7) и `GOAL.md` обновляются только подтверждёнными фактами.
